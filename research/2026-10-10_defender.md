> The owner's machine (24 logical CPUs, Windows 10.0.26300, Defender platform 4.18.26080.4-0). F1 and F2 are the owner's

## F1 — what Defender costs a file workload (the owner's probe, 2026-10-10)

The probe writes 4 000 fresh 4 KB files named `f<i>.js` in its OWN new folder under `D:\rsd\_defender_probe\`, reads them
back, then deletes only that folder. A background job samples `\Process(MsMpEng)\% Processor Time` every 500 ms. Core-seconds
= the average percentage / 100 × (the workload's seconds + 5).

| Run | Exclusions | Wall time | MsMpEng, average | Defender core-seconds |
|---|---|---|---|---|
| 1 | none | 9.1 s | 612 % | ≈ 86 |
| 2 | none | 10.6 s | 714 % | ≈ 112 |
| 3 | folder exclusions (F2) | 4.1 s | ≈ 87–90 % | ≈ 8 |
| 4 | folder exclusions (F2) | 3.5 s | ≈ 87–90 % | ≈ 8 |

The workload ran about **2.5 × faster**, and Defender used about **12 × less CPU** for it. The ≈ 90 % that remains is
Defender's background work during the run. It is not work on the excluded files.

## F4 — what the design takes from this

- **The checkbox reads its state without elevation.** It replays the 5007 events for `Exclusions\Paths` (and for
  `Exclusions\Processes`, to warn if any process exclusion exists). For each folder, a newest event with a
  `New value: …\Exclusions\Paths\<folder> = 0x0` line says "excluded". **A removal's event has not been seen on this
  machine** (nobody removed one). Until a real removal is captured (E16.S5's first *uncheck*, with the owner's consent),
  any other 5007 shape that names the folder reads as *not known*, never as "not excluded".
- **When no 5007 event names a folder,** the log does not reach back to its last change (about three months on this
  machine), or the folder was never excluded. The state is then *not known*. It is never shown as "not excluded".
- **An exclusion set by policy** (`HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`, Intune, GPO) was not
  measured. The story says that it is not seen.
- **On this machine the replay gives all three folders as excluded,** so the checkbox reads back as checked. This is
  the owner's requirement.
- **Only the change needs elevation.** It needs one UAC prompt for add or remove. The same elevated script then reads
  the list back with `Get-MpPreference`, and its exit code says whether the list now matches what was asked. Then the
  unelevated replay sees the new 5007 events.
- **Defender's CPU can be recorded every full run without elevation,** from the cumulative raw counter. A full run that
  sees a different pid (a reboot, or a Defender restart) starts a new baseline and does not compute a difference. The
  hours between the last read and the restart are not covered. The record says how many hours it covers.
- **The read is not free.** It took 7.3 s cold. It joins the disk script's one CIM session (the commit line already
  queries `Win32_PerfRawData_PerfOS_Memory`) and is timed in E15.S10 before it ships.
- **This machine has no "before" history.** The exclusions came before the first per-run record. So a weekly saving
  measured on this machine needs a before-period it does not have (Q6 in the plan). F1's probe is the only before /
  after figure. *Measure now* repeats it as an A/B: the same workload in an excluded folder and in a folder that is not
  excluded.
